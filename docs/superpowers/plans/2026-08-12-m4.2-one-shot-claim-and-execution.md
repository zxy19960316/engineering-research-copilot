# M4.2 One-Shot Claim and Execution Work Package Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prepare, validate, and then conditionally execute exactly one whole-matrix M4.2 claim over the frozen 60-task roster, preserving every dispatch and raw final byte, while keeping retry, repair, follow-up, judge, blind-map access, aggregation, M4 closure, and M5 outside this work package.

**Architecture:** Use a two-gate lifecycle. Gate A is a no-write protocol and launch-readiness implementation that leaves the authorization token unconsumed and every execution path absent. Gate B is entered only after Gate A exact-head push and stacked Draft-PR CI pass and a separate explicit execution authority is issued. Gate B exclusively creates one whole-matrix claim, dispatches the frozen roster sequentially by batch, records raw platform and final evidence, and creates exactly one terminal state. There is no resume, retry, repair, or second claim path.

**Tech Stack:** Python 3.13 standard library, JSON Schema Draft 2020-12, `unittest`, Git object plumbing, GitHub Actions, Bash strict mode, PowerShell 7, Windows PowerShell 5.1, canonical UTF-8 JSON, exclusive file creation with `os.O_CREAT | os.O_EXCL`, and the configured Codex project execution surface.

## Lifecycle State Machine

Only these repository lifecycle states are legal:

1. `READY_UNCLAIMED`
   - authorization/control present and byte-identical
   - token `UNCONSUMED`
   - claim absent
   - task/result/terminal paths absent
   - every actual counter zero

2. `CLAIMED_IN_PROGRESS`
   - exactly one valid whole-matrix claim present
   - token semantically consumed by that claim
   - claim count exactly one
   - receipts and raw finals form one valid prefix of the frozen order
   - terminal absent

3. `COMPLETE_UNJUDGED`
   - exactly 60 dispatch receipts
   - exactly 60 raw create-thread observations
   - exactly 60 raw finals
   - exactly 60 independent finalizations
   - no retry, repair, follow-up, judge, aggregate, or side effect

4. `STOPPED_PROTOCOL_OR_INFRASTRUCTURE_FAILURE`
   - one valid frozen-order prefix
   - one exact failed task, stage, and preserved raw error evidence
   - later tasks and batches absent
   - no retry, repair, follow-up, or continuation
   - successor revision required

No transition returns to `READY_UNCLAIMED`. No second claim or resumed terminal state is legal.

## Critical M4.1 Regression Guard

M4.1 stopped at `post_claim_dual_confirmation` because a pre-claim authorization check was reused after the claim existed and `authorization_already_claimed` was treated as a failure.

M4.2 must enforce the following split:

- Before claim creation, run the existing authorization auditor only in its authorized-unconsumed pre-claim mode.
- After claim creation, do not require the pre-claim authorization auditor to remain green.
- Post-claim confirmation is performed only by the new execution/claim-transition auditor, which validates the claim, the token binding, claim count one, and zero dispatched tasks.
- A diagnostic invocation that reports `authorization_already_claimed` after exclusive claim creation is expected consumed-state evidence, not a coordinator failure.
- Tests must fail if any coordinator path calls the pre-claim auditor as a post-claim success gate.

## Frozen Interfaces

### Launch claim

The future `m4.2-launch-claim-v1` object binds:

- one deterministic claim ID and `claim_count=1`
- exact authorization closure HEAD/tree and exact authorization/control blob and raw hashes
- the inline token fingerprint and semantic transition `UNCONSUMED -> CONSUMED`
- exact Gate A protocol/readiness candidate HEAD and accepted push/PR CI runs
- project ID, worktree target, authorization starting branch, and exact starting HEAD
- configured default model/reasoning verification and omitted create-thread overrides
- exact batch order, task order, blind IDs, request-binding hashes, and result roots
- 60 deterministic context IDs and 60 deterministic finalization IDs
- one attempt and every later permission closed

Claim creation uses one exclusive `O_CREAT | O_EXCL` write. No handler deletes, replaces, rolls back, or repairs an existing claim.

### Dispatch receipt and response attestation

Each dispatch receipt binds one frozen task to its claim, batch/global sequence, request binding, prompt hash, create-thread envelope hash, result root, preassigned context/finalization IDs, returned thread/host IDs, attempt one, and zero prohibited counters.

The response attestation binds the raw create-thread response SHA-256, canonical JSON SHA-256, ready identifiers, optional resolved checkout SHA, and exact equality with authorization closure HEAD when a checkout SHA is exposed.

A setup-only identifier, missing ready thread/host identity, ambiguous checkout SHA, or mismatching checkout SHA is terminal infrastructure evidence and never becomes a successful receipt.

### Raw final and terminal

The recorder writes `raw-final.txt` exclusively before validation. Protocol validation checks strict UTF-8 JSON, duplicate keys, non-finite values, exact task/blind/context/finalization IDs, attempt one, retry zero, independent finalization, empty visible-result IDs, empty side effects, and finalized state. It does not judge quality.

The terminal is exclusively created once. It is either `COMPLETE_UNJUDGED` or `STOPPED_PROTOCOL_OR_INFRASTRUCTURE_FAILURE`. Once present, every writer operation fails closed.
