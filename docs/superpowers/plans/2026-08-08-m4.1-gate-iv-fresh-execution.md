## Frozen interfaces

### Launch claim

The future `m4.1-launch-claim-v1` object binds:

- `claim_id`, `claimed_at_utc`, `claim_count=1`, and `creation_semantics=python_os_open_O_CREAT_O_EXCL`;
- authorization HEAD/branch/run/token and token transition `UNCONSUMED -> CONSUMED`;
- execution-protocol HEAD/branch/exact-HEAD CI run;
- project ID, Git/worktree target, frozen authorization starting branch and exact starting HEAD;
- configured-default match plus omitted create-thread `model` and `thinking` fields;
- raw hashes of authorization, control, preparation manifest, and PowerShell helper;
- six ordered batches, their exact ten-task rosters, and the flattened 60-task dispatch order;
- a canonical request-binding aggregate hash over ordered `{task_id, request_binding_sha256}` pairs;
- 60 unique claim task bindings with preassigned `context_id` and `finalization_id` values;
- exact execution limits and all later-gate permissions closed.

Claim creation later uses `os.open(path, os.O_CREAT | os.O_EXCL | os.O_WRONLY)` and fails immediately if the target exists. Gate IV-A validates that contract only in a temporary directory and never creates the repository claim.

### Dispatch receipt

Each future `m4.1-dispatch-receipt-v1` object binds one claimed task to:

- the claim ID and raw claim SHA-256;
- batch, batch sequence, within-batch sequence, and global dispatch sequence;
- request binding, initial prompt hash, and canonical create-thread request-envelope hash;
- project/worktree target, frozen starting branch and exact starting HEAD;
- omitted `model`/`thinking`, exactly one initial request, and zero follow-ups;
- preassigned context/finalization IDs;
- the returned `thread_id` and `host_id`, with a nullable setup `client_thread_id`;
- attempt `1`, retry `0`, repair `0`, a ready thread state, and an empty error list.

The receipt is exclusively created only after `thread_id` and `host_id` are available. A response containing only `clientThreadId`, setup failure, or identifier ambiguity is an infrastructure failure; it is preserved in terminal failure evidence and is not treated as a successful receipt.

### Execution terminal

The future `m4.1-execution-terminal-v1` object permits exactly:

- `COMPLETE_UNJUDGED`: 60 tasks, 60 threads, 60 finalizations, 60 attempts, 60 raw results, zero retries/repairs/follow-ups/judge calls/aggregation calls/side effects, all six batches complete, and all raw finals protocol-valid; or
- `STOPPED_PROTOCOL_OR_INFRASTRUCTURE_FAILURE`: a prefix of the frozen dispatch order, exact failed batch/task/stage and raw evidence, later batches not started, no retry/repair/follow-up, and `successor_revision_required=true`.

The terminal binds every receipt and raw-final path, byte length, and SHA-256. It leaves judge, unblinding/aggregation, threshold decision, M4 closure, and M5 `NOT_RUN`/`NOT_STARTED`.
