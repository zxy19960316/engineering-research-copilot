# M3.1.1 R3 Acceptance Repair Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Repair the M3.1.1 acceptance architecture without changing immutable r2 evidence, then prepare five contract-consistent r3 cases for independently authorized one-shot fresh-context evaluation.

**Architecture:** Keep the M3 method-bundle validator strict and unchanged for successful bundles. Add a deterministic composer that combines a validated immutable M2 bundle with a compact model payload, a case-level eligibility auditor that stops conflicts before a prompt is frozen, and a separate forward-outcome validator that accepts either a valid bundle or the exact expected F03 block. Preserve r2 by hash, keep F04 upstream preparation independent from M3 implementation, and make r3 manifests explicitly supersede r2 for acceptance without deleting history.

**Tech Stack:** Python 3.12 standard library, `unittest`, UTF-8 JSON without BOM, SHA-256 raw and canonical hashing, PowerShell, Git, the existing M1/M2/M3 validators, and GitHub Actions only after all local gates are green and push is separately authorized.

## Global Constraints

- Branch from immutable r2 evidence HEAD `6ec576a47a804300e2a95e6bddfff1d00c5270a3` as `codex/m3.1.1-r3-acceptance-repair`.
- Never overwrite, delete, normalize, repair, or relabel any file under `evals/m3/results/forward-r2/` or `evals/m3/forward-inputs-r2/`.
- Call the new work r3, never an r2 retry. Record `supersedes_for_acceptance` while retaining r2 as historical failed evidence.
- Keep M3 `IN_PROGRESS` and M4 `NOT_STARTED` until all five r3 outcomes, deterministic gates, and exact closure-HEAD CI succeed.
- Do not execute a route, experiment, simulation, training job, model inference, download, service, upload, deployment, resource allocation, or operational/safety action.
- Do not consume a fresh context until its case eligibility result is exactly `eligible`, its prompt and immutable input are frozen, and the user has explicitly authorized the one-shot run.
- Preserve one finalization and one case-validator invocation per fresh case. Never strip fences, extract a substring, repair JSON, retry a case, or rewrite a failed output.
- Treat offline fixtures, replay, synthetic inputs, and deterministic composer tests as structural evidence only.
